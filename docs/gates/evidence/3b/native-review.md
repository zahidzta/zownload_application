# 3B-04 Windows synthetic review — 2026-10-31

This is a native Windows **Rust queue fixture**, not a completed Tauri WebView walkthrough. It runs the real Windows queue, SQLite, process supervisor, ZIP writer, and filesystem using a locally compiled deterministic engine stand-in. All generated media and archives stayed under unique `%TEMP%/zownload-zip-queue-*` roots; no request touched the owner's Downloads folder. Rust 1.99.1 compiled the stand-in, whose yt-dlp and FFmpeg executable SHA-256 was `7C0E9A9BD81F2C10C475DFD15168EFFA274A7A18B68A9BC6D87BCAAEE5486C51` for each copy. The [toolchain record](../../../toolchain.md#gate-3b-windows-zip-verification) lists setup and pinned production hashes.

The fixture requested five playlists in FIFO order with ZIP enabled, then changed Settings to ZIP off. Every request retained its captured choice and output folder. It used 2 MiB synthetic MP4 entries with an ordinary failed entry, duplicate titles, an all-failed playlist, and a simulated disk-full stderr. The completed output directory contained only:

| Archive | Stored entries (2,097,152 bytes each, method 0) |
|---|---|
| `Playlist.zip` | `first.mp4`, `second.mp4` |
| `Playlist (1).zip` | `first.mp4`, `second.mp4` (mixed playlist; failed entry omitted) |
| `Playlist (2).zip` | `first.mp4`, `first (1).mp4` |

There was no published ZIP for the all-failed or disk-full job and no `.zip.part` at settlement. SQLite had zero queue rows, three History rows, and three persistent notifications: `playlist_summary:2:1`, `playlist_summary:0:2`, and `disk_full` with the synthetic engine stderr. The fatal job's owned work directory was absent. `packaging` events were observed for the successful and mixed jobs. The writer tests separately cover an existing archive collision, interrupted append recovery, idempotent recovery after final rename, and removal of only the recovered owned archive. A restart test committed entry 0 to the ZIP before advancing SQLite, reopened a paused queue, and continued at entry 1 without duplicating entry 0; it also exercised an older persisted entry-directory path.

The 5 ms sampler reported **5 peak staging files and 8,389,117 peak staging bytes**, including ZIP journal/manifest files. It saw **2 current media files** during FFmpeg tagging, when the source and tagged output coexist. The numbers are sampled peaks from the 2 MiB fixture, not a proof of a byte-for-byte upper bound for arbitrarily large media. The strict reading of NFR-04 and Gate 3B's one-current-media-file rule is therefore **not met** by the existing FFmpeg pipeline; an owner decision on that rule was requested. The ZIP writer itself deletes each completed media file after its archive commit.

On 2026-10-31, the owner approved revising FR-54 and NFR-04 to allow the partial ZIP plus temporary work files for only the current entry, with cleanup after archive verification and before the next entry. The observed source and tagged output are consistent with that rule. This synthetic sampler does not establish the real-engine peak or complete the native-app review.

**V3 passed** in the documented clean detached checkout: UI tests, sequential Node tests, Rust format, and `scripts/verify-foundation.ps1`. The full V2 and focused Windows queue, playlist, and process-tree tests also passed; see [3B-03 verification](3b-03.md). A local attempt to set an isolated temporary directory ACL for a real permission-denied output fault was rejected by automatic command approval policy. The existing Rust I/O classifier has focused disk-full and permission-code tests, but no end-to-end Windows output-permission observation was recorded.

## Native WebView and real-engine review

On 2026-10-31, the native Windows Tauri WebView at `tauri.localhost` submitted ZIP-enabled playlists through its visible controls. Settings pointed to output folders under the unique disposable root `%TEMP%/zownload-3b-review-23ca9de0541f421fbc6bc4038037b28d`; app data and the local HTTP fixture server (`127.0.0.1:38642`) were isolated there too. No request used the owner's Downloads folder. The server supplied generated valid MP4s through ordinary HTML playlists accepted by the pinned yt-dlp. The real executable SHA-256 values were yt-dlp `66674953FE251B89F4D08C5F0E35E0728679BD67AB3D7D05C0562AF101DD3E7A`, FFmpeg `FA050630DDF5B7C3303D8DAB5E5A42E7023547FB78EC9B90B5BE0A4F788A7E66`, and QuickJS `BEC67F8F87FA22958D3AB8BE5508088116B8BFF90032323D82C94545E1698B83`. The app was built with a temporary Tauri config overriding app directories; `build.rs` was timestamp-refreshed so the debug binary used bundled `tauri.localhost` assets. The earlier synthetic Rust fixture remains the disk-full simulation.

An initial real-engine, two-entry `Gate 3B Local Playlist.zip` contained `one.mp4` and `two.mp4`, each uncompressed (ZIP method 0) and CRC-valid. Killing the app while a later two-entry playlist appended its second item exposed a real bug: append overwrote the previous central directory, so truncating to the journal boundary alone could not reopen the ZIP. The fix saves only the old ZIP central directory/footer in a small recovery sidecar before append, then restores it when needed. A second interruption exposed a Windows retry collision with the completed `source.mp4`; a synced per-entry `ready.json` now lets Continue reuse verified staged media, while incomplete downloads keep their `.part` data.

The final controlled `Gate 3B Resume Proof` run killed the native app during its second archive append. At kill, the pending ZIP was 33,407,966 bytes; the journal still committed only entry 0 at 29,475,784 bytes. The recovery sidecar was 98 bytes and the staged-media marker was 103 bytes. On native restart the UI showed paused 1/2. Clicking Continue restored the committed boundary and finished `Gate 3B Resume Proof.zip` with `medium-one.mp4` and `medium-two.mp4`, each 29,475,636 bytes, method 0 and CRC-valid. The queue settled to zero rows, History gained one row, and the owned work directory was removed. The first entry was not duplicated.

The three-entry `Gate 3B Mixed` fixture had two `dup.mp4` URLs and one missing MP4 URL. Its archive contained `dup.mp4` and `dup (1).mp4`, each 2,951,273 bytes, method 0 and CRC-valid; the failed entry was omitted. The WebView showed “2 correct, 1 failed”; SQLite recorded `playlist_summary:2:1`, one History row, and no queue row. Downloading that playlist again in the same folder preserved `Gate 3B Mixed.zip` and created `Gate 3B Mixed (1).zip` with the same two valid entries.

The real-engine 5 ms sampler took 6,965 samples during the mixed playlist. Its observed peak was **7 staging files, 11,805,745 staging bytes, 2 current media files, and 1 entry work directory**. The peak snapshot comprised the pending ZIP (5,902,831 bytes), current `source.mp4` (2,951,236), current `ready.mp4` (2,951,273), journal (93), manifest (126), recovery sidecar (91), and `ready.json` (95). This is a sampled peak for this fixture, not a universal byte bound. It shows only the current entry's source and converted output beside the partial archive; committed entries had no retained work directories.

For the permission fault, an ACL deny for write/create was applied only to an isolated `%TEMP%/denied-final` folder; an independent write probe confirmed Windows access denied. The native app targeted that folder for the same playlist. It displayed “Storage permission denied.” SQLite then had zero queue rows, unchanged History count, and a persistent `permission_denied` notification with WinError 5 detail. The denied folder and owned work directory were empty; no yt-dlp or FFmpeg child remained. The ACL was restored and writing to the folder was verified. The earlier synthetic fixture covers disk-full settlement; no shared volume was filled.

After these fixes, focused ZIP writer, staged-media, queue lifecycle, and process-tree tests passed, as did the full Rust test suite. The exact Gate 3B **V3 passed** in a clean detached checkout with pinned Node 24.22.0 and `npm ci`: UI tests, sequential Node tests, Rust format, and foundation verification. These observations satisfy the 3B-04 native review; Gate 3B still awaits explicit owner acceptance of its checkpoint.
