# Gate 3C-03 — installed NSIS/MSI upgrade review

V2 completion is **pending**; both NSIS and MSI scenarios passed in the latest run, but a stale native exit code failed the step after evidence was written, preventing its upload. The `Windows installed upgrade review` workflow builds older and candidate packages from explicit source refs, then runs clean install, launch, same-format updater, relaunch/version, and uninstall scenarios on an isolated `windows-latest` runner. It serves signed local updater metadata and checks that NSIS requests the NSIS package and MSI requests the MSI package. No owner installation is used.

## Preliminary NSIS findings

- Run [41291930395](https://github.com/zahidzta/zownload_application/actions/runs/41291930395) (`85b2a40`) and [41295033138](https://github.com/zahidzta/zownload_application/actions/runs/41295033138) (`79cc005`) both built the previous and candidate NSIS/MSI pairs and passed package-signature and tamper-rejection checks.

The tracked old app process had exited. The script stopped at NSIS, before testing the MSI updater scenario.

It did not change the observed outcome. The root cause is not confirmed; the hook is not considered a fix without a passing rerun.
- [FR-75](../../../../PROJECT.md#fr-75) calls for a “New version available” message with a direct download link if a package updater proves unreliable. This fallback has **not** been implemented; owner review is required before changing the app’s update behavior.

## Installer process lifetime correction

Run [41352914073](https://github.com/zahidzta/zownload_application/actions/runs/41352914073) confirmed the NSIS package transfer completed while the installed version remained `0.0.0`. Inspection found that `Supervisor::install` puts the app in a Windows job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Tauri's updater starts its installer with `ShellExecuteW`, then calls `std::process::exit(0)`. An installer inheriting that job is killed when the app exits, before it can complete installation. Waiting in an NSIS preinstall hook cannot protect it from job termination.

The correction temporarily enables `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` only around Tauri's installer launch, after downloading and verifying the signed package. Existing child processes remain contained, supervised commands still enter their own jobs, and normal inheritance is restored if installation returns. See [Microsoft's job inheritance rules](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects#managing-processes-in-jobs). The Windows process-tree regression checks installer survival, media cleanup on parent exit, and restored inheritance after launch returns.

The automatic V2 scenario now uses `previous_ref=task-3c-02-03`, `candidate_ref=task-3c-02-03`, `previous_version=0.0.0`, and `candidate_version=0.0.1`. Both test versions are built from the corrected source: the old app launches the update, so changing only the candidate cannot fix the old app's job inheritance. This proves a controlled version upgrade; it does not claim that the uncorrected `main` build can update itself. No app release has been published. A passing run must record clean install, launch/version, matching-format update, relaunch/version, and uninstall for both NSIS and MSI. Full V2 remains pending the owner's CI result.

The separate ZIP restart test now waits for its background worker to release the coordinator's SQLite reference before removing its temporary directory. Queue settlement occurs before that worker exits, so dropping only the test's coordinator reference did not guarantee the Windows database files were closed.

## Verifier exit status correction

- Run [41365909345](https://github.com/zahidzta/zownload_application/actions/runs/41365909345) passed both formats' clean install, matching updater, relaunch, and uninstall scenarios and wrote the evidence file. The step then returned 1 without a new assertion failure.
- The expected Minisign rejection of a tampered package left `$LASTEXITCODE=1`. The [GitHub Actions PowerShell footer](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#exit-codes-and-error-action-preference) propagates that native status even after later PowerShell commands succeed. The new regression reproduced the same successful signature messages followed by exit 1 before the correction.
- `verify-windows-release.ps1` now captures each Minisign process result explicitly, including expected rejection, and exits 0 only after all signed-package checks and cleanup complete. This also avoids PowerShell 5.1 treating expected native stderr as a terminating error. Verification and metadata errors still throw; success is not returned from `finally`.
- `scripts/test-windows-release-exit.ps1` passed in Windows PowerShell 5.1 and PowerShell 7 with the real Minisign verifier and the repository's signed fixture. The Actions-style caller returned 0 for valid packages plus rejected tampering and continued after verification; invalid package signatures and invalid metadata after the signature checks both returned 1. The workflow runs this regression before the installer builds. Setup and exact commands are in [the toolchain notes](../../../toolchain.md#gate-3c-signature-verifier-regression).
- Script parsing, relative Markdown links, and whitespace checks passed. A successful workflow and uploaded V2 evidence remain pending the pushed rerun and owner review. No installer was executed on the owner's account.
